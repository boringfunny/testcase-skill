# AI实现检查交接（V5 5.0.0，沿用V3判定与2.3.0状态）

XMind供测试人员理解需求和测试思路；Excel供其他AI检查整体实现，帮助安排后续人工测试。本skill生成设计、表格与回填规范，不新增查源码或执行游戏的模式。

## 判定口径

【已通过】表示已有证据说明代码或配置的处理符合测试点关键条件和预期结果；静态证据足够即可通过，不以实机为统一前提。只找到同名函数、配置项、注释、未接入的分支或搜索命中不能通过；需说明相关入口、关键条件及结果处理，按实际需要核对调用关系和数据配置。只有部分链路明确时如实记录。

| 总状态 | 使用条件 |
|---|---|
| 【未开始】 | 尚无有效检查记录；生成时明确项留空，也按未填写单列统计 |
| 【部分验收】 | 已检查部分处理，但关键链路或检查点未查清 |
| 【验收受阻】 | 因源码、配置、权限、工具能力或外部材料缺失，无法继续判断实现 |
| 【待确认】 | 需求、预期或适用范围未明确；当前实现不能替代批准 |
| 【未通过】 | 有证据证明明确要求不满足，可由代码或配置差异支持 |
| 【已通过】 | 关键条件和结果的实现符合需求，且证据充分；允许运行未验证和后续测试建议并存 |
| 【不适用】 | 已确认该版本或范围不适用，记录依据；没找到实现或没有实机环境不等于不适用 |

三层结果位于检查详情：配置核对、代码核对、运行验证，选未验证/部分验证/符合/不符/待确认/不适用。未采用层填未验证，不为使公式通过而填不适用。配置或代码一层足以覆盖该点时可整体通过；如果某层已有不符，不可被另一层符合掩盖。已记录部分验证或仍影响结论的待确认，应先明确缺口；明确不符与另一未决Q共存时可未通过，但分别说明判定范围。

“没找到实现”注明查过哪些目录、配置和调用路径、哪些未能访问；不能直接推断整个项目未实现。疑似问题写具体待查点，不包装为确定缺陷。静态检查通过是实现层结论，不冒充实机结果；也不因没有实机结果而统一降为部分验收。

## 主表：每天优先阅读

“AI实现检查”默认打开，十列固定为：编号、模块、优先级、测试点、需求简述、AI检查状态、实现说明、最短验收路径、问题编号、详情。

- F状态、G实现说明是唯一结论回填位置；H最短验收路径是设计内容，初次生成就填写，检查AI可依据已确认的入口与准备条件修正；I保留原Q，可追加本轮新发现Q并在问题页登记，不能静默删除未决依赖。详情不维护另一份总状态和同义结论。
- E需求简述复用xmind_points，缺少时显示原测试点标题，完整预期在详情；不截断或机械删词。
- G通常一句，必要时两句：写关键条件、处理、结果；不符直接写差异。如“按当日累计金额判断，跨阈值后增加1个达标日”。不得每行重复“已查静态、未实测、不能通过”。
- H写“必要前提 → 游戏内操作 → 关键观察结果”，通常1行，必要时2行；不能只写风险问题或“测试是否正常”。路径不是已执行记录，也不是静态通过前提。新设计必须填写；旧计划无路径时留空并在报告列出缺项，不把旧建议或代码核对步骤机械拼接为游戏路径。
- 点击编号或详情跳到同ID详情，详情可返回；跨页公式与跳转使用ID查找，允许两表独立排序。不要修改稳定ID。

## 详情与共用基线

“检查详情”A-M保存编号、标题、完整条件与操作、预期与观察、影响、性质、规则/覆盖ID、原文证据、思路、完整备注及导图定位。C-M默认折叠，可展开，完整文本仍在单元格中。长备注超过行高显示能力时展开编辑栏阅读，不据辅助预览截断判断丢失。

N实现检查证据；O检查范围例外；P检查方式例外；Q/R/S三层结果；T批准记录；U缺口/不适用原因；V补充记录；W缺陷/任务号；X检查者例外；Y检查时间例外；Z版本/提交例外；AA反馈提示；AB返回；AC模块供汇总。

总览B17、B18、B19、B20、B21分别登记共用版本/提交、检查范围、检查方式、检查者、时间。详情O/P/X/Y/Z留空时使用共用值，有例外填写本条完整覆盖值，不填含糊的“同上”。共用范围可以说明本轮只查客户端或服务端、未查外部依赖，具体缺口仍按例记录。

N证据逐例保存，不用共用基线代替：配置写文件、表项、字段及值；代码写文件:行号、函数、关键分支或调用路径，版本由有效基线提供；实际运行过才附操作、截图、日志及前后值。多种证据分项列，不笼统套用“多方式交叉验证”。引用其他场景日志不能伪装为本例运行。

遇规则问题在问题页保存原文/缺口、需确认、影响用例；批准后在详情T写结论、批准人、日期、版本，保留原设计。已通过须有明确依据或已批准口径，不能以现有代码代替策划决议。

设计阶段主表F明确项留空、待确认项预设待确认，G和详情N-Z、总览共用基线全部留空；H预填设计的最短验收路径，不计作验收反馈。准备页是供人工测试的建议，不是AI静态检查的运行门槛。初始稿不得预填检查通过；修订设计不继承历史结果。

## 反馈、统计与兼容

AA只提示缺填和明显矛盾：方式、检查范围、人员/时间/版本可继承共用值，实现说明与可定位证据须逐例填写。配置/代码符合且运行未验证可通过提示检查；已有不符却填通过、未获批Q、全为未验证或关键内容仅部分验证会提示。纯运行证据充分时也可支持实现判断。

公式无法确认真实代码存在、链路是否充分、证据真假或引用的Q是否全部获批；“反馈已填写”不等于自动判通过。部分验收、受阻、待确认、不适用需在U/V写具体原因和下一步/依据，不为满足必填而编造事实。所有总状态由检查AI结合证据填写。

总览标题“AI实现检查结果”，分别统计空白、七种新状态、旧待实测/已验收/其他见备注、反馈已填写和无效状态。不适用单列，不计通过，不把此统计称为实机通过率。七张表保留完整规则覆盖、执行准备和变更信息，日常仅需阅读主表及相关详情。

旧状态不在新下拉，复制进新表时兼容识别并提示逐条复核，禁止批量提升为已通过。导出器从设计计划创建新表，不导入或迁移已回填工作簿。用户要求迁移须另存，按ID保留历史证据与原结论后逐条复核，不能从旧套话推断静态检查已充分。

回填后重算汇总；未经原生重算时按原始状态计数，不使用旧缓存。原生兼容性、结构检查、AI实现检查和人工实测分别说明。

## V3服务端优先与客户端简查

十列主表和七种状态不变。检查详情“条件与操作”及完整备注保存review_focus，执行准备“所需能力与环境”附检查目标和清单。按需求核对配置、关键条件、处理及结果；实际定位证据仍逐例填N，checks不是已经查过的记录。

服务端代码或配置充分覆盖关键条件与结果时可已通过，运行未验证可保留。仅配置中存在奖励、不明入口是否调用、失败分支未查清，不能完整通过。

客户端简查若预期是实际显示、动画播放或适配效果，仅资源、配置或代码存在不足以证明表现符合。可记录已确认的静态部分；缺实际效果证据时按情况填部分验收或验收受阻，并写明最短验收路径。不是所有客户端需求都必须实机：若该条仅要求配置值正确，充分的配置证据即可；按本条实际预期判断。

待确认问题页E列将impact和关联ID共同显示，原有F-K回填位置不变。影响说明是设计内容，批准记录仍需后续回填；不以代码现状代替需求批准。公式不具备理解画面或静态证据充分性的能力，不给已通过自动背书。
