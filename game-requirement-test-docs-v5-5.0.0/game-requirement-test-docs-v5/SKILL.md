# 游戏模板测试设计与交接 V5

调用 `$game-requirement-test-docs-v5`。与原版、V2、V3及V4独立共存，脚本、参考和资产均取自本目录，不改动其他技能。每次使用新的输出目录，保留原件与历史回填。

交付同批测试点的 `<需求名称>-测试用例.xmind`、`<需求名称>-AI验收表.xlsx`。XMind帮助测试人员快速理解需求；Excel供后续AI检查实现、为人工测试提供依据。本技能只设计和导出文档，不读取游戏源码检查实现、不操作游戏、不预填验收结果。

## 输入与规划

- 使用用户选择的需求；未指定时列工作区“游戏需求”候选，单一匹配直接使用，多份无法判断再问。正文缺失或读不清不凭标题补规则。
- 测试思路文件依次采用用户指定、工作区 `outputs/**/通用游戏测试思路.xlsx`、[随包快照](assets/通用游戏测试思路.xlsx)。多个不同版本不按修改时间擅自裁定；用快照时说明。先按思路条目规划适用范围，再结合需求选方法和编写用例，不先写完用例再补引用。
- 历史XMind仅参考层次和表达：选2～3份相关本地样本，无样本使用[随包样本](assets/style-samples)，不能从历史需求继承当前业务规则。
- 沿用schema_version为2的规则模型；技能版本5.0.0不等于计划格式升级。旧计划与旧图转换保持原设计，不能自动归为服务端用例。见[兼容与变更](references/change-and-migration.md)。

## 设计流程

先读[模板展示规则](references/template-presentation.md)、[设计方法与证据](references/design-and-evidence.md)和[计划契约](references/plan-contract.md)。

1. 提取本次资料，记录路径、定位和指纹；逐项检查相关图片、批注与修订，提取成功不等于理解完成。可用 `--ideas`、重复 `--style` 指定来源。
   ```text
   python <skill>/scripts/read_sources.py --workspace <工作区> --requirement <需求文件> --out <工作目录>/evidence.json
   ```
2. 从需求提炼规则与缺口，按思路文件选适用方向，引用真实条目编号。保留需求验证、边界派生、补充建议、待确认的区别。没有适用条目可说明原因，不硬套模板。
3. 继续使用直接验证、等价类、边界值、决策表、状态迁移、风险经验。记录模型和选择理由；不强制每种方法都用、不凑数量、不无依据扩张风险。
4. 服务端为主：写明配置约束、条件判断、请求处理、状态与资产结果。每例填写 `review_focus.target="服务端"` 及具体 `checks`。步骤以核对条件、追踪处理、确认结果为主；保留可供人工后续测试的前置、数据、触发和清理，但不强加登录、点击、截图。只描述业务对象，不编造表、字段、接口、函数或代码位置。
5. 纯客户端布局、文字、动画等集中到末尾UI检查，按具体业务分组附少量简查，标 `target="客户端简查"`；结果需独立判断时拆开，不把不同预期硬合并。涉及资格、奖励、金额或时间的服务端返回数据仍需详细检查。按风险定优先级，不把客户端全部设为P2。纯客户端需求可只输出简查，不虚构服务端处理。
6. 待确认标题直接提问，gap写已知与缺口，ask写具体问题，impact用一句话写影响；一个业务问题复用同一个Q。需求不明才建Q，未找到实现写检查缺口，缺环境写准备限制。具体写法见计划契约。
7. 每例编写 `acceptance_path`，以“必要前提 → 游戏内操作 → 关键观察结果”提供最短验收路径，通常1行、必要时2行。现成账号优先；需要特殊数据、时间或工具写明需准备，不虚构入口、GM命令。待确认项只描述触发现象和记录内容；游戏内无法直接验证的内容明确说明限制与必要工具，不能用连点替代重复回调验证。路径不代表执行结果，不能要求实机通过才允许静态通过。写法见计划契约。
8. 详细设计完成后人工编写 `xmind_points`，通常1条、必要时2～3条。保留关键数字、范围、限制和概率，不机械截断。导图短句表达场景与业务结果，检查清单放完整备注和Excel详情。

9. 根据需求类型选择template_profile，并逐例填写display_group和display_path；主功能用具体业务名。分类不替换原path，不为填满模板增加用例。用template_decisions记录分类取舍，只进入辅助报告。随包四模板只提供结构和样式，模板中的时间、补发、关联系统不得直接当成需求。

## 导出与交接

读取[验收约定](references/acceptance-contract.md)。新V5设计用严格校验导出：

```text
python <skill>/scripts/build_documents.py --plan <工作目录>/plan.json --evidence <工作目录>/evidence.json --out <新输出目录> --require-v5
```

`--require-v5`要求template_profile、每例display_group/display_path/xmind_points，以及V3原有review_focus、acceptance_path和Q的impact齐全。保留`--require-v3`供旧计划严格检查。兼容旧计划时省略该参数；旧导图保真转换另加 `--allow-legacy`，不添加检查目标、不补造覆盖。需求修订可加 `--baseline <上次输出>/.support/design-baseline.json`，稳定ID不因排序或版本升级重编号。

- XMind保持“模块 → 测试点 → 简短描述”，按入口、红点、具体主功能、特殊点验证、异常状态、配置检查、UI检查排序，只显示有测试点的分类；完整规则见模板展示参考。完整检查项、执行设计与证据存备注。待确认测试点保留短问题及Q编号；问题页保留原文/缺口、需确认、影响说明与用例。
- Excel仍为七页，默认打开十列“AI实现检查”；F/G是唯一总状态、实现说明回填位置；H“最短验收路径”由设计提供，后续AI可依据已确认条件修正。详情保存检查项及证据；共用版本、范围、方法、人员、时间只填一次。问题影响写入原问题页，检查目标与清单写入现有详情、执行准备，不新增工作表。
- 七种状态与V2 2.3.0相同。充分的配置/代码证据可支持已通过，允许运行未验证和后续测试建议并存。只找到函数、相关配置或部分调用关系不够；实际画面、动画效果不能凭代码或资源存在判通过。
- 生成时预填最短验收路径，只有待确认项预设状态，其余检查结果留空。公式只提示缺填与明显矛盾，不自动证明实现充分；旧状态单独统计，不迁移历史结论。
- 缺少简述的旧V2计划保留原详细分支并提示，不静默缩写。旧字段缺失不猜测补写。输出拒绝覆盖，`.support`保存基线、验证报告和辅助预览。

依赖xlsxwriter、openpyxl、Pillow；读PDF另需pypdf。优先现有Python，桌面可用load_workspace_dependencies定位。缺依赖按当前允许方式处理，不擅自联网安装。

## 验证与交付

检查来源与Q、规则与思路引用、用例ID、两文件详细内容、简述归属、初始空回填、统计、跳转、ZIP完整性和源文件保护。查看主表、核对项、问题页、准备页及导图预览。原生打开与重算单独记录；结构自测不能替代兼容性或语义质量判断。

交付主文档并说明设计计数、排除/暂缓/待确认范围、未执行检查；区分已确认、推导建议、未知与失败尝试。不能把登记项映射完整称为需求100%覆盖。真实质量评测见[评测方法](references/evaluation.md)。

维护后运行 `python <skill>/scripts/self_test.py --work-dir <新目录>` 及技能结构校验。`scripts/install.py`完整复制技能、拒绝同名覆盖。发行ZIP先隔离安装验证，再安装独立V5；不得修改或替换任何既有版本。
