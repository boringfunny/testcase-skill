# 设计方法与证据

## 规则与事实

每个事实规则引用真实路径、表/单元格、段落、图片锚点或PDF页。保留冲突、修订有效性不明、读不清、正式配置缺失等问题。历史样本仅提供结构和风险线索，不证明当前资格、价格、计日或补发政策。

`需求验证`为原文明示；`边界派生`为原文逻辑推导；`补充建议`为风险建议；`待确认`为无法确定判定口径。推导写理由；建议的需求证据只是上下文，不等于建议获批。建议若要形成硬性通过/失败标准且尚无依据，标待确认并关联Q。

一个可解释的业务约束为一条规则；同一句包含资格、消耗、奖励、次数可拆规则。标题、重复与非业务段落无需造规则，但source_review记录读取范围、排除类型和缺口。规则列表经内容审查后才作为本轮设计分母，脚本不自动判定原文是否理解完整。

## 方法选择

| 规则特征 | 方法 | 记录 |
|---|---|---|
| 单一明确交互或输出 | 直接验证 | 可观察结果、依据、影响 |
| 输入范围或分类处理 | 等价类 | 有效/无效分区及代表值 |
| 数量/金额/等级/时间阈值 | 边界值 | 阈值、单位、最小步长、选值；不一律N±1 |
| 多条件共同决定结果 | 决策表 | 条件组合和结果；不可达/结果无关的理由 |
| 领取、消费、重试、重登、过期 | 状态迁移 | 起始状态、事件/守卫、目标状态及动作；适用非法迁移 |
| 历史缺陷、弱网等风险 | 风险经验 | 风险机制、适用条件、依据或缺口 |

矩阵可表示为多条coverage_items，每项保留model。不要求每种方法都使用，不凑数全排列。组合过多按风险选择并注明未覆盖范围；不能凭成对覆盖推断关键结算链路充分。

## 游戏适用检查

- 资格/入口：投放、解锁AND/OR、未达/刚达、刷新、跳转、结束；有该机制才展开。
- 资产/奖励：逐档道具/数量、未达/可领/已领；显示、资产增减、领取标志、重登持久化分别观察。
- 时间：时区、计日点、自然日/满时长、在线/离线跨点、请求跨点、迟到回调；不默认0点或本地时间。
- 异常：适用的连点、重复回调、弱网、重登、维护与幂等；支付只提出沙盒准备要求，本技能不操作支付。
- 关联：任务、进度、红点、共享资源、账号/角色隔离；共享范围须有依据。
- UI/配置：图文数值冲突、正式/测试参数、可读性与适配；没有性能阈值不自行定义合格帧率或耗时。

优先主流程、资产、核心结算；按损失影响、发生条件、改动范围及历史缺陷解释P0/P1/P2。不机械地全部P0，不虚构发生概率。时间×领奖、弱网×消耗等交叉仅在存在机制时使用。

## 粒度与审查

用例可沿多个状态完成业务链路，包含多个检查点；不要求一步一条。需要不同前置、独立判定或分别重试的变体分独立ID，用导图父节点分组。实质重复仅在不同环境确有风险理由时保留。

执行者应知道如何准备角色、数据、时间，触发什么，在哪里/何时观察，如何恢复环境。能力未知写待准备，不发明命令、接口、日志字段或数据库表。

反查：原文→规则遗漏；规则→覆盖项适用；覆盖项→用例真实验证；用例→预期获依据支持。结构校验只证明引用存在，不能证明这些语义判断正确。

## V3：把思路落实为服务端检查

先阅读通用思路，按本需求挑选相关方向并保存ideas引用，再制定规则覆盖。条目可提供测试风险和方法，不能当作新的业务要求。原思路包含显示、跳转、红点时，识别其背后的服务端条件与数据；纯表现保留简查，不从“入口隐藏”推断未授权请求一定需要返回某个错误码。

| 检查对象 | 用例需要说清楚 | 不可替代的依据 |
|---|---|---|
| 配置 | 哪个业务参数、值、单位、范围、适用版本与需求比对 | 实际配置路径和项由检查AI提供 |
| 条件与流程 | 入口如何到达处理、条件何时判断、正反分支结果 | 只找到同名函数或孤立判断不足 |
| 状态与资产 | 成功/拒绝后哪些值变化、哪些不变、是否保存 | 更新与落地结果不能只凭界面状态推测 |
| 异常与关联 | 重复、跨日、回调等为何适用于本需求 | 未明确的补偿、重试、时间政策先提Q |

每例checks写实际核对内容，例如“积分阈值100与需求一致；未领取且积分>=100才发1份奖励；重复请求不再增加奖励”，不能只写“检查配置、检查代码”。每项必须有来源或明确的推导/建议性质。共享数据范围、时区、清零时间、落库方式没有依据时不可当成事实。

步骤可以写“沿奖励请求的处理核对资格判断，确认失败分支不发奖”；observe写“资格分支、资产变更与领取状态更新的对应证据，实际位置由检查AI填写”。不要虚构函数、日志字段或数据表。verification优先建议静态代码、配置或二者交叉核对，requirements列所需材料与版本；后续运行数据和触发条件保留，缺环境不能冒充需求缺口。

客户端简查按模块归纳文字、布局、动画等相关表现，但独立可失败的结果分例。不通过增加截图步骤伪装服务端检查；不把服务端数据检查写成“界面显示正确”就结束。纯客户端需求允许全部简查，无须服务端数量占比。

审查时逐项反查：需求→规则→适用思路→覆盖方法→checks→结果依据；数量减少不等于质量提高。资产、资格、阈值、时点、次数、归属范围不能为了简洁漏掉。


## V5补充

V5新设计按需求类型选择随包模板，仅借用组织样式。先按通用测试思路和需求完成设计，再逐例确定唯一display_group/display_path。客户端简查统一放末尾UI检查；不再按业务模块各建客户端分支。候选方向与排除理由写template_decisions，不为模板补造跨日、补发或英雄机制。
